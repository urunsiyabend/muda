# Phase 13.1: Rendering Performance Optimization - Research

**Researched:** 2026-03-27
**Domain:** Rust immediate-mode UI rendering — layout caching, glyphon buffer reuse, viewport virtualization, dirty-flag invalidation
**Confidence:** HIGH (all major claims verified against codebase source or official docs)

---

## Summary

This phase optimizes an existing wgpu + glyphon + custom immediate-mode UI framework to sustain under 4ms frame times with 10 tabs and sidebar open. The research examined: (1) the existing codebase's render loop and element lifecycle, (2) glyphon/cosmic-text's internal caching capabilities, (3) LRU cache APIs already in use in the project, and (4) GPUI/Zed's hybrid immediate+retained approach as inspiration.

The current architecture re-shapes every glyphon `Buffer` from scratch on every frame, re-lays out every element regardless of change, and renders every sidebar entry regardless of scroll position. These three problems account for the bulk of frame budget waste. All three have well-understood solutions that map cleanly onto the existing codebase without replacing the render loop.

The project already uses the `lru` crate (v0.12, in `Cargo.toml`) for `TextureCache`. The same pattern can be used directly for the glyph content cache. The dirty-entity system (`dirty_entities: HashSet<EntityId>` in `AppContext`, `cx.notify()` observers) already exists as the backbone for view-level dirty flags.

**Primary recommendation:** Implement in three independent, additive passes: (1) glyph buffer cache with LRU eviction, (2) per-view dirty flags with layout result caching, (3) viewport virtualization for sidebar and editor text lines.

### Pattern 1: Glyphon Buffer Content Cache

**What:** A global `LruCache<(u64 /*line_hash*/, u32 /*font_size_bits*/), glyphon::Buffer>` that stores pre-shaped buffers. On each frame, `measure_text_cached()` in `TextSystem` computes a fast hash of the text string, looks up the cache, and returns the existing `Buffer` if found — skipping `FontSystem::set_text()` + `shape_until_scroll()` entirely.

**When to use:** Any text rendering call where the text content is the same as a previous frame. Especially effective for editor lines (mostly unchanged), line numbers, file tree labels.

**Key insight from cosmic-text docs:** A `glyphon::Buffer` internally caches shaped glyphs at the `BufferLine` level. Its shape cache invalidates only when text or metrics change. Therefore, a buffer that hasn't changed since last frame costs almost nothing to re-prepare — but we still allocate and drop it every frame. The content cache moves allocation out of the hot path entirely.

**Cache key design:**
```rust
// Source: codebase inspection + cosmic-text docs (deepwiki.com/pop-os/cosmic-text)
#[derive(Clone, Copy, PartialEq, Eq, Hash)]
pub struct GlyphCacheKey {
    /// FNV/FxHash of the text string bytes — fast, non-cryptographic
    pub text_hash: u64,
    /// Font size stored as f32 bits (exact comparison, no float issues)
    pub font_size_bits: u32,
    /// Line height stored as f32 bits
    pub line_height_bits: u32,
}
```

**Cache structure in TextSystem:**
```rust
// ora/src/rendering/text.rs — add to TextSystem struct
use lru::LruCache;
use std::num::NonZeroUsize;

pub struct TextSystem {
    // ... existing fields ...
    /// Global content cache: (text_hash, font_size_bits, line_height_bits) -> shaped Buffer
    /// Capacity: 2048 entries covers ~40 visible lines * 10 open files + sidebar + gutter
    glyph_cache: LruCache<GlyphCacheKey, glyphon::Buffer>,
    /// Hit/miss counters for --show-fps reporting
    cache_hits: u64,
    cache_misses: u64,
}

impl TextSystem {
    pub fn new(device: &Device, queue: &Queue, surface_format: wgpu::TextureFormat) -> Self {
        Self {
            // ... existing init ...
            glyph_cache: LruCache::new(NonZeroUsize::new(2048).unwrap()),
            cache_hits: 0,
            cache_misses: 0,
        }
    }

    /// Measure text, returning a cached Buffer if content is unchanged.
    /// The returned Buffer is owned by the caller for this frame only —
    /// it is NOT returned to the cache. The cache holds the previous frame's
    /// version. A new Buffer is inserted at end-of-frame.
    pub fn measure_text_cached(
        &mut self,
        text: &str,
        font_size: f32,
        line_height: f32,
        max_width: Option<f32>,
    ) -> (glyphon::Buffer, Size<f32>) {
        let key = GlyphCacheKey::from_text(text, font_size, line_height);
        if let Some(cached_buf) = self.glyph_cache.pop(&key) {
            self.cache_hits += 1;
            // Re-measure from existing shaped buffer (layout_runs() is O(n_lines), no re-shaping)
            let size = measure_from_buffer(&cached_buf, line_height);
            return (cached_buf, size);
        }
        self.cache_misses += 1;
        self.measure_text(text, font_size, line_height, max_width)
    }

    /// Return a used Buffer to the cache after paint is complete.
    /// Called by the paint dispatcher after all PaintCommand::Text are submitted.
    pub fn return_buffer_to_cache(&mut self, key: GlyphCacheKey, buffer: glyphon::Buffer) {
        self.glyph_cache.put(key, buffer);
    }

    pub fn cache_hit_rate(&self) -> f32 {
        let total = self.cache_hits + self.cache_misses;
        if total == 0 { return 0.0; }
        self.cache_hits as f32 / total as f32
    }
}
```

**CRITICAL:** The `glyphon::Buffer` in `PaintCommand::Text` is consumed by `TextSystem::add_text_area()` which moves ownership. The cache return pattern requires either (a) storing the key alongside the buffer in `PaintCommand::Text` and returning it after `render_frame()` completes, or (b) using `Arc<Mutex<Buffer>>` (avoid — contention). Option (a) is correct: extend `PaintCommand::Text` to carry `Option<GlyphCacheKey>` and add a post-render cache-return pass in the event loop.

### Pattern 2: Per-View Layout Dirty Flags

**What:** Each view (sidebar, text area, gutter, tab bar, status bar) maintains a `bool` dirty flag. The frame loop checks this flag: if clean, the cached `Vec<LayoutOutput>` and paint commands from the previous frame are reused. If dirty, the view re-lays out and the result is stored.

**Key constraint from CONTEXT.md:** The element tree ALWAYS rebuilds (cheap Rust allocs). Only layout computation and text shaping are skipped.

**What triggers dirty:**
- Window resize → all views dirty
- Model/data change via `cx.notify()` → the affected view marks dirty
- Theme/font change → all views dirty
- Scroll position change → does NOT mark layout dirty, only updates visible slice

**What does NOT trigger dirty (paint-only):**
- Hover state change → re-paint only (no layout)
- Caret blink → timer wakes `about_to_wait`, requests redraw, no layout change
- Transition animation progress → re-paint only

**Where dirty flags live:**
The existing `AppContext::dirty_entities: HashSet<EntityId>` already tracks which model entities have changed via `cx.notify()`. The per-view dirty flag can be a simple `bool` on each view struct, set in the view's `update()` method when its model entity notifies.

**Implementation sketch:**
```rust
// Views get a dirty flag — example: SidebarView
pub struct SidebarView {
    // ... existing fields ...
    layout_dirty: bool,
    cached_layout: Option<Vec<LayoutOutput>>,
}

impl SidebarView {
    /// Called when SidebarPresentation model notifies.
    pub fn mark_dirty(&mut self) {
        self.layout_dirty = true;
        self.cached_layout = None;
    }

    /// Called on window resize.
    pub fn mark_all_dirty(&mut self) {
        self.layout_dirty = true;
        self.cached_layout = None;
    }
}
```

**Event loop integration:** The layout phase in `RedrawRequested` checks each view's dirty flag. If clean, `request_layout` still runs (tree rebuild is kept) but `compute()` is skipped and the cached `layout_outputs` are reused. The flexbox `compute_flexbox()` call is the expensive part — that's what the dirty flag gates.

### Pattern 3: Viewport Virtualization

**What:** For the sidebar file tree and editor text area, only render the rows that are visible within the scroll viewport plus a half-screen buffer zone in each direction.

**Sidebar flat-list virtualization (VS Code pattern):**
```rust
// ora/src/views/file_tree.rs
impl FileTreeView {
    pub fn render_virtualized(&self, cx: &mut ViewContext, scroll_offset_px: f32, viewport_height: f32) -> AnyElement {
        const ROW_HEIGHT: f32 = 22.0;  // uniform height — monospace label rows
        const BUFFER_ROWS: usize = 20; // half-screen buffer above and below

        let flat_list = self.presentation.flatten_to_visible(); // existing flat list logic
        let total_rows = flat_list.len();
        let total_height = total_rows as f32 * ROW_HEIGHT;

        let first_visible = (scroll_offset_px / ROW_HEIGHT).floor() as usize;
        let visible_count = (viewport_height / ROW_HEIGHT).ceil() as usize + 1;

        let start = first_visible.saturating_sub(BUFFER_ROWS);
        let end = (first_visible + visible_count + BUFFER_ROWS).min(total_rows);

        let top_spacer = start as f32 * ROW_HEIGHT;
        let bottom_spacer = (total_rows - end) as f32 * ROW_HEIGHT;

        // Render: top spacer + visible rows + bottom spacer
        // ... build Div tree for [start..end] rows only
    }
}
```

**Editor text lines:** The `TextAreaView` already slices `visible_lines` from `RenderModel` (the adapter's `build_render_model()` produces only the visible slice). Confirm this slice includes the ±20 buffer rows. No structural change needed — verify the slice size is correct.

**Scroll position change:** The `scroll_offset_px` is a `SharedScrollOffset` (`Rc<Cell<f32>>`). Changing it does NOT mark layout dirty — the virtualization function reads it fresh each frame to compute the visible slice. This is already how smooth scrolling works in the event loop.

### Anti-Patterns to Avoid

- **Caching glyphon Buffers with interior mutability (Arc/Mutex):** Glyphon's `Buffer` is not `Send`. Keep the cache single-threaded on the same `TextSystem` owner.
- **Returning Buffers to cache while atlas is trim()-ing:** `TextSystem::clear()` calls `atlas.trim()`. The cache holds `Buffer` objects that reference atlas entries only by ID — buffers can be cached across frames safely, but the atlas trim removes unused glyph bitmaps. If a cached Buffer's glyphs are evicted from the atlas, `prepare()` will re-rasterize on next use (this is correct behavior, not a bug).
- **Storing GlyphCacheKey hashes with std DefaultHasher:** Rust's `DefaultHasher` is non-deterministic across process restarts (randomized). For a single-session cache (which this is), it's fine. For testing reproducibility, use `FxHasher` from `rustc-hash`.
- **Marking all views dirty on every mouse move:** `MouseMoved` fires at ~1000Hz. The event loop's `request_redraw()` call on mouse move is correct, but layout dirty should NOT be set from hover changes — those are paint-only.
- **Virtualizing the tab bar:** Per CONTEXT.md decision, tab bar virtualization is out of scope. Tabs are typically <20 entries; the complexity is not justified.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| LRU eviction for glyph cache | Custom linked-list LRU | `lru::LruCache` (already in Cargo.toml) | Correct O(1) eviction, battle-tested, project already uses it for TextureCache |
| Hash for cache key | Custom hash | `std::collections::hash_map::DefaultHasher` or `rustc_hash::FxHasher` | Hand-rolled hashes frequently have collision bugs; FxHash is what rustc itself uses |
| Flat-list virtualization math | Custom tree virtualization | Simple index arithmetic on pre-flattened `Vec<(depth, node)>` | The tree is already flattened in FileTreeView; virtualization is just slice indexing |
| Flexbox layout caching | Custom layout diffing | Dirty flag + re-run `compute_flexbox()` only when dirty | The existing `compute_flexbox()` is already correct; caching its output is trivial |
| GPU profiling | Custom timer infrastructure | `wgpu-profiler` crate | Timer queries, nested scopes, Tracy export already solved — but only add if --show-fps is insufficient |
| Degradation logic | Complex state machine | Simple frame counter + threshold check | 3 consecutive slow frames → disable animations; 1 fast frame → re-enable |

**Key insight:** Every "new" thing needed is either already in the codebase (LRU, dirty entities) or is a direct application of existing patterns (slice indexing for virtualization, dirty flag for layout skip).

## Common Pitfalls

### Pitfall 1: Buffer Ownership in PaintCommand::Text

**What goes wrong:** `PaintCommand::Text` takes ownership of `glyphon::Buffer`. After `render_frame()` consumes the commands, the buffer is dropped. The cache return requires capturing the buffer before it's dropped.

**Why it happens:** The current design moves `Buffer` into `PaintCommand::Text` for sound ownership. Modifying this to support cache return is the trickiest part of the glyph cache.

**How to avoid:** Extend `PaintCommand::Text` to carry `cache_key: Option<GlyphCacheKey>`. In `GpuState::render_frame()`, after processing all commands, collect `(key, buffer)` pairs and return them to the caller. The event loop's `RedrawRequested` handler calls `gpu_state.text_system.return_buffers_to_cache(returned_pairs)` after `render_frame()` completes.

**Warning signs:** If buffers are never returned to cache, hit rate stays at 0%. Log cache hit rate in the --show-fps output to detect this immediately.

### Pitfall 2: Dirty Flag Scope Too Coarse

**What goes wrong:** Marking ALL views dirty when any model changes. This defeats the purpose — if the sidebar model updates but the editor model is unchanged, only the sidebar should re-layout.

**Why it happens:** The existing `cx.notify()` / `dirty_entities` system doesn't distinguish which view was affected — it tracks entity changes, not view dirty state.

**How to avoid:** Each view subscribes to its own model entity via the observer system. The subscription callback sets `view.layout_dirty = true` for that specific view only. Window resize is the only global dirty trigger.

**Warning signs:** Cache hit rate in layout is near 0% even when only typing in the editor (only editor and gutter should be dirty, not sidebar).

### Pitfall 3: Scroll Does Not Mark Layout Dirty (But Must Update Slice)

**What goes wrong:** After scrolling, the virtualized sidebar renders the old slice because the dirty flag wasn't set (correct!) but the visible slice wasn't recomputed (incorrect!).

**Why it happens:** The scroll offset changes are NOT model notifications — they bypass `cx.notify()` and go directly through `shared_scroll_offset: Rc<Cell<f32>>`. The virtualization code must read scroll offset fresh each frame, not cache it.

**How to avoid:** In the virtualized render function, always read `scroll_offset_px` from the live `SharedScrollOffset` cell. The dirty flag gates layout computation; the scroll slice is always recomputed from current scroll position during the render phase (which always runs).

**Warning signs:** Sidebar shows wrong entries after scrolling even though the frame is rendering.

### Pitfall 4: glyphon Atlas Trim vs Cached Buffers

**What goes wrong:** `TextSystem::clear()` calls `atlas.trim()` which removes glyph bitmaps for unused glyphs. If a cached `Buffer` references atlas entries that were trimmed, the next `prepare()` call will re-rasterize — which is correct behavior. But if `clear()` is called BEFORE the cache return (i.e., buffers in the current frame's commands are returned after the next `clear()`), they may reference stale atlas state.

**Why it happens:** The frame lifecycle is: render_frame() → clear() (next frame start). If cache return happens after clear(), the returned buffers are fine (they hold shaped glyph positions, not atlas references). This is actually safe.

**How to avoid:** The glyphon `Buffer` stores shaped glyph run data (positions, glyph IDs) independently of the atlas. The atlas only matters during `prepare()`. Returning a buffer to cache after `clear()` is safe because the buffer's internal shaping data is still valid — only atlas bitmaps are evicted, and they re-rasterize on demand.

**Warning signs:** None specific — this pitfall is a false alarm once understood. Document it to prevent over-engineering.

### Pitfall 5: Hover/Caret Blink Triggering Layout

**What goes wrong:** Hover state changes on `MouseMoved` (1000Hz) or caret blink timer firing triggers `request_redraw()` which triggers a full layout pass.

**Why it happens:** The current event loop calls `request_redraw()` on every `MouseMoved` event. Without dirty flag gating, layout runs every mouse move.

**How to avoid:** The dirty flag on each view must ONLY be set by model changes and window resize. `MouseMoved` triggers redraw but layout dirty stays false — only the paint phase runs. The key: `LayoutContext::compute()` is only called when `layout_dirty` is true for that view's subtree. Mouse move events set no dirty flags, so compute() is skipped and cached `layout_outputs` are reused.

**Warning signs:** Frame time does not improve on mouse move if layout dirty is still being set from hover events.

### Pitfall 6: LRU Cache Capacity Too Small

**What goes wrong:** Cache thrashes — entries are evicted before they can be reused the next frame.

**Why it happens:** A 40-line visible editor + 500-entry sidebar + gutter + status bar + tab bar = ~600 unique text strings per frame. If capacity is 512, common entries are evicted before the next frame.

**How to avoid:** Set initial capacity to 2048 entries. This covers all visible text in a maximally loaded scenario with headroom. At ~1-2KB per cached buffer (shaped glyph data), this is ~2-4MB memory — acceptable. Expose capacity via --show-fps or a debug flag so it can be tuned.

**Warning signs:** Cache hit rate plateaus at 60-70% instead of 90%+. Increase capacity in 512-entry increments.

### Glyphon Buffer Reuse (verified via cosmic-text docs)
```rust
// Source: deepwiki.com/pop-os/cosmic-text — BufferLine caching section
// Buffer maintains internal ShapeLine and LayoutLine caches per line.
// Calling set_text() + shape_until_scroll() on an existing Buffer reuses
// harfbuzz plan caches when the text content is unchanged.
// If you hold the same Buffer and call shape_until_scroll() without set_text(),
// NO re-shaping occurs — it returns immediately from cache.
//
// For the glyph content cache: pop buffer from LRU, verify content matches
// (via the pre-computed hash), skip set_text() if hash matches. The buffer
// is already shaped; measure_from_buffer() reads layout_runs() directly.
fn measure_from_buffer(buffer: &glyphon::Buffer, line_height: f32) -> Size<f32> {
    let mut max_width = 0.0f32;
    let mut total_lines = 0;
    for run in buffer.layout_runs() {
        max_width = max_width.max(run.line_w);
        total_lines += 1;
    }
    let height = if total_lines > 0 { total_lines as f32 * line_height } else { line_height };
    Size::new(max_width, height)
}
```

### Fast String Hashing for Cache Key
```rust
// Source: Rust Performance Book (nnethercote.github.io/perf-book/hashing.html)

use std::hash::{Hash, Hasher};
use std::collections::hash_map::DefaultHasher;

fn hash_text(text: &str) -> u64 {
    let mut hasher = DefaultHasher::new();
    text.hash(&mut hasher);
    hasher.finish()
}
```

### Viewport Virtualization Slice Indexing
```rust
// Source: Pattern derived from VS Code's flat-list tree implementation
// (referenced in CONTEXT.md as "proven approach for tree views")
fn visible_slice(flat_list: &[(usize, &FileTreeNode)], scroll_px: f32, viewport_h: f32)
    -> (usize, usize, f32, f32)
{
    const ROW_H: f32 = 22.0;
    const BUFFER: usize = 20;
    let total = flat_list.len();
    let first = (scroll_px / ROW_H).floor() as usize;
    let count = (viewport_h / ROW_H).ceil() as usize + 1;
    let start = first.saturating_sub(BUFFER);
    let end = (first + count + BUFFER).min(total);
    let top_pad = start as f32 * ROW_H;
    let bot_pad = (total - end) as f32 * ROW_H;
    (start, end, top_pad, bot_pad)
}
```

### Frame Degradation Guard
```rust
// Source: CONTEXT.md decision — "3+ consecutive frames exceeding budget"
// Track in OraApp (event_loop.rs)
struct FrameDegradation {
    consecutive_slow: u32,
    degraded: bool,
}

impl FrameDegradation {
    fn update(&mut self, frame_ms: f64) {
        if frame_ms > 4.0 {
            self.consecutive_slow += 1;
            if self.consecutive_slow >= 3 {
                self.degraded = true;
            }
        } else {
            self.consecutive_slow = 0;
            self.degraded = false;
        }
    }
    fn is_degraded(&self) -> bool { self.degraded }
}
```

## State of the Art

| Old Approach | Current Approach | Impact |
|--------------|------------------|--------|
| Create new `glyphon::Buffer` every frame | Cache shaped Buffers by content hash, reuse across frames | Eliminates harfbuzz shaping cost for unchanged lines — the dominant CPU cost |
| Run `compute_flexbox()` every frame for all views | Dirty flag per view; skip compute when clean | Eliminates O(n_elements) flexbox passes for unchanged views |
| Render all sidebar entries regardless of scroll | Viewport virtualization: render visible ± 20 buffer rows only | Sidebar with 500+ entries renders same as 20 entries |
| Hover/blink triggers full layout pass | Paint-only invalidation for non-layout changes | Mouse movement (1000Hz) no longer causes layout work |

**Current state (as-built):**
- `TextSystem::measure_text()` creates a new `Buffer`, calls `set_text()`, calls `shape_until_scroll()` — full shaping every call (HIGH cost)
- `LayoutContext::compute()` calls `compute_flexbox()` unconditionally every frame — no caching
- `FileTreeView` renders all visible entries in a Div column — no virtualization
- `CaretElement` uses global `BLINK_EPOCH`/`LAST_ACTIVITY` statics — already correct, no layout triggered
- `request_redraw()` on `MouseMoved` is already in the event loop — layout dirty gating needed

## Open Questions

1. **Exact LRU capacity for glyphon cache (Claude's Discretion)**
   - What we know: TextureCache uses capacity param; 2048 buffers at ~1-2KB each is ~2-4MB
   - What's unclear: Exact per-Buffer memory footprint in glyphon 0.7 + cosmic-text
   - Recommendation: Start at 2048. Add `glyph_cache_capacity` to debug flags. Tune based on hit rate measurement in --show-fps.

2. **Caret blink: does it currently trigger layout?**
   - What we know: `about_to_wait()` calls `request_redraw()` when `next_blink_instant` passes; no `cx.notify()` involved
   - What's unclear: Whether the subsequent `RedrawRequested` runs layout even without dirty entities
   - Recommendation: Inspect the `RedrawRequested` handler — it runs `layout_cx.compute()` unconditionally today. The dirty flag work will fix this automatically.

3. **Buffer cache return: is PaintCommand::Text the right extension point?**
   - What we know: The buffer is moved into `PaintCommand::Text`, consumed by `add_text_area()`, then dropped
   - What's unclear: Whether extending PaintCommand is cleaner than an alternative approach (e.g., returning buffers from `render_frame()`)
   - Recommendation: Have `GpuState::render_frame()` return `Vec<(GlyphCacheKey, glyphon::Buffer)>` of all consumed Text commands; the event loop inserts them into the cache after frame. This keeps `GpuState` ignorant of the cache.

4. **Should FileTreeView::flatten_to_visible() be cached?**
   - What we know: The flat list is reconstructed each frame from `FileTreePresentation`
   - What's unclear: How expensive the flatten is for 500+ entries
   - Recommendation: Cache the flat list alongside the dirty flag. Invalidate on presentation change. This is a micro-optimization but straightforward.
