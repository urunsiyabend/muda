## Measurements

### Frame breakdown (2310 frames)

| Bucket | Count | CPU avg | CPU max | view avg | GPU/present avg |
|---|---|---|---|---|---|
| Cool (view<0.5ms, cache hit, paint-only) | 440 | 0.75ms | 2.70ms | 0.31ms | 3.89ms |
| Hot (view≥2ms, full rebuild) | 1731 | 6.56ms | 104.10ms | 5.89ms | — |

### Cache hit rates

- **Glyph cache:** 99% (cumulative, session-wide)
- **Layout cache:** 88–89% cumulative; rises to 90%+ during continuous editor-scroll bursts (as PaintOffsetElement keeps LayoutIds stable frame-to-frame)

### Representative continuous editor-scroll burst

```
FRAME 7.1ms | view 0.3 layout 0.3 prepaint 0.1 paint 0.0 gpu 6.4 | glyph 99% layout 88%
FRAME 7.3ms | view 0.3 layout 0.3 prepaint 0.1 paint 0.0 gpu 6.6 | glyph 99% layout 89%
FRAME 6.7ms | view 0.3 layout 0.3 prepaint 0.1 paint 0.0 gpu 6.1 | glyph 99% layout 89%
```

CPU work = 0.7ms. The 6-7ms `gpu` column is vsync wait on the user's 144Hz monitor (6.94ms cycle); the frame is display-refresh-bound, not CPU-bound.

### Outliers

- Max frame: 106.8ms (single event) — `view=103.1ms` on frame 11:34:39. Correlates with a file-open / workspace change (syntax highlighting cold-start). One-shot, not a steady-state cost.

## Issues Encountered

- **`FrameDegradation` threshold cosmetic issue:** Guard fires `[DEGRADED]` for any frame >4ms for 3+ consecutive frames. On a 144Hz monitor (6.94ms cycle), vsync-capped frames show as DEGRADED even when CPU work is <1ms. Not a real regression — frame budget is the display-refresh period, not 4ms. **Deferred:** threshold should be refresh-rate-aware. Tracked as a follow-up note.
- **Release vs debug uncertainty in the log:** no command-line recorded. Mitigated by evidence from cool-frame CPU being release-consistent regardless.

## Off-Plan Work Completed During Phase 14.1

During Phase 14.1 execution (outside Plan 03's scope but relevant to the phase outcome):

- **Text-area scroll flicker fix (commit `ce5a2ac`):** pre-existing bug where text characters flickered / disappeared during scroll at line boundaries. Root cause: `TextElement` defaulted to `Length::Auto` width, producing `w=0` glyphon `TextArea.bounds` for empty lines; those bounds were cached across paint-only frames and then clipped new text when the row transitioned from empty to non-empty. Fix: wrap each line in a `flex_row` Div and give `TextElement` `grow(1.0)` so bounds width tracks the row independently of text content. User visually confirmed the fix.
- **glyphon 0.7 → 0.10 + wgpu 23 → 28 upgrade** (commit `a1fa765` and follow-ups): Rust toolchain pinned to 1.92.0 for glyphon 0.10 MSRV; `cosmic-text 0.15` API migrated (set_rich_text signature change); wgpu 28 API migrated (Instance descriptor, device descriptor, render-pass descriptor, pipeline descriptor); `gpu_allocator`/`windows` crate conflict resolved via `cargo update -p windows@0.58.0 --precise 0.62.2`.
- **Rich-text infrastructure:** `TextRun` struct added, `TextSystem::measure_rich_text_cached` / `paint_rich_text_cached` added, `TextElement::rich(Vec<TextRun>)` constructor added — powers per-span color in syntax-highlighted lines.
- **Shrink guard in layout cache** (commit `29c2499`): forces full layout when `new_layout_count != cached_layout_outputs.len()` in either direction.
- **FileTreeView spacer stability** (commit `6a00ad0`): top/bottom virtualization spacers always emitted (even at h=0) to prevent ±1 child count variation during sidebar scroll.
- **F12 paint-command dump** (commit `ede4940`): one-shot diagnostic armed by F12 keypress — dumps every paint command (Rect, StyledRect, Text, Scissor, Offset, LayerBoundary) for one frame. Kept intentionally; zero per-frame cost.
