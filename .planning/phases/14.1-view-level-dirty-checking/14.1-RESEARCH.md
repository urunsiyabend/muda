# Phase 14.1: View-Level Dirty Checking + Paint-Phase Scroll - Research

**Researched:** 2026-03-28
**Domain:** Custom GPU-accelerated UI rendering pipeline optimization — view-level dirty tracking, paint command caching, scroll without relayout
**Confidence:** HIGH (codebase verified directly; Zed GPUI patterns verified via source fetch)

---

## Summary

Phase 14.1 is a targeted refactor of ora's rendering pipeline to eliminate full layout
recomputation on scroll. The current architecture already has a `needs_layout` dirty flag
and a single flat `cached_layout_outputs` vec. The problem is that scroll unconditionally
sets `needs_layout = true` (line 958 of event_loop.rs), because visible_lines changes
with each scroll, which changes the element tree structure, which invalidates LayoutIds.

The goal is to break that coupling. Zed GPUI solves this with two orthogonal mechanisms:

1. **View-level dirty tracking** (`dirty_views: FxHashSet<EntityId>`) — clean views skip
   `render()`, `prepaint()`, and `paint()` entirely; their cached prepaint state and paint
   commands are replayed. This is `reuse_prepaint()` + `reuse_paint()`.

2. **Paint-phase coordinate translation for scroll** (the `UniformList` pattern) — instead
   of changing the element tree on scroll (which requires relayout), scroll offset is applied
   as a paint-phase coordinate translation. The element tree structure stays constant across
   scroll frames; only the Y-offset changes during paint.

For ora, the translation is as follows:

- **Tab bar, sidebar, status bar, gutter:** These do not scroll during editor scroll. They
  need per-view paint command caches so their output can be replayed without re-running the
  element pipeline.
- **Editor (TextAreaView + GutterView):** The current architecture mutates the element tree
  on scroll — changing `visible_lines` (which changes child count, LayoutIds, and layout
  results). The fix is to keep `visible_lines` count constant and handle the fractional pixel
  offset via `PushOffset` in paint (already done for `scroll_y_offset_px`) but also replace
  the `dispatch_command(Scroll(delta_lines))` → rebuild model cycle with a stable-element-count
  approach where the same N lines (viewport height) are always in the tree and only their
  content changes when the window scrolls by a full line.

**Primary recommendation:** Implement in two parts: (1) per-view paint command caches for
static views (tab bar, sidebar header, status bar, gutter), and (2) stable visible_lines
count so editor scroll stays paint-only. This eliminates `needs_layout = true` on scroll.

## Architecture Patterns

### Current Frame Rendering Flow (Problem State)

```
WindowEvent::MouseWheel
  → dispatch_command(Scroll(delta))          // changes adapter state (scroll_y)
  → shared_scroll_offset.set(px)             // fractional offset updated
  → needs_layout = true                       // ← ROOT CAUSE: why this is set
  → request_redraw()

RedrawRequested:
  → ora_window.render()                       // builds fresh element tree
    → EditorRootView::render()
      → adapter.build_render_model()          // queries visible_lines with new scroll_y
      → TextAreaView::new(model)              // clones new visible_lines
  → element_tree.request_layout()            // ALL elements get fresh LayoutIds
  → layout_cx.compute()                      // full flexbox (expensive)
  → element_tree.prepaint()
  → element_tree.paint()
  → gpu_state.render_frame(&commands)
```

The problem: `visible_lines` changes on each line-boundary scroll, changing child count in
the element tree, which changes LayoutId ordering. The cache check `new_layout_count >
cached_layout_outputs.len()` forces full layout even when all elements are the same size.

### Target Architecture (After Phase 14.1)

```
WindowEvent::MouseWheel (editor scroll):
  → fractional px offset updated only          // NO dispatch_command unless line boundary
  → needs_layout = false                        // ← KEY: scroll is paint-only
  → redraw requested

RedrawRequested (scroll frame):
  → ora_window.render()                         // builds element tree
  → element_tree.request_layout()              // LayoutIds assigned (fast)
  → cached_layout_outputs reused               // compute_flexbox SKIPPED
  → prepaint: static views check dirty flag
    → if !dirty: reuse_prepaint(cached hitboxes)
    → if dirty: run prepaint
  → paint: static views check dirty flag
    → if !dirty: replay cached PaintCommand slice
    → if dirty: run paint, cache commands
  → gpu_state.render_frame()
```

### Pattern 1: Stable Visible-Lines Count

**What:** Keep the number of visible lines constant across scroll frames. The line count
equals `floor(editor_height / LINE_HEIGHT)`, which only changes on window resize — not on
scroll. When scrolling by one line, the same N slots exist in the element tree; only their
content (text, line number) changes. This keeps child count stable → LayoutIds stable →
cached_layout_outputs valid.

**When to use:** Always for editor TextAreaView and GutterView.

**How it works today (broken):** The adapter sets `scroll_y` (first visible line index)
and `build_render_model()` queries exactly `viewport_lines` lines starting from `scroll_y`.
So the count IS already stable at `viewport_lines`. But `needs_layout` is still forced true.

**The actual fix:** The `needs_layout = true` on scroll can be removed if the element tree
layout is actually stable. Verify: on scroll, does anything change that requires layout?
- `scroll_y_offset_px` changes (fractional px) → used as `mt(scroll_shift)` on Div
- `visible_lines` content changes → changes text content, which changes glyphon Buffers
- `visible_lines[i].is_current_line` may change → affects bg color, not size
- Line number content changes → text reshaping, but character count is bounded (same digit count)

The `mt(scroll_shift)` margin-top change IS a layout mutation today. This must move to
paint-phase offset (PushOffset), similar to how ScrollArea already works.

### Pattern 2: Paint-Phase Offset for Fractional Scroll

**What:** The fractional line offset (`scroll_y_offset_px = scroll_top_px % LINE_HEIGHT`)
currently appears as `mt(-scroll_y_offset_px)` on Div elements in TextAreaView and
GutterView. Margin-top changes require layout recomputation. The fix is to remove these
margin-top mutations and instead apply `PushOffset(0.0, -scroll_y_offset_px)` in the paint
phase, just like `ScrollArea` already does.

**Precedent in codebase:** `ScrollArea::paint()` calls `cx.push_offset(0.0, -scroll_y)`.
The same pattern is used for the editor scroll fractional offset.

**When to use:** For TextAreaView and GutterView fractional scroll offset.

**Example (current broken approach):**
```rust
// In TextAreaView::render() — causes layout dependency on scroll offset
let scroll_shift = -self.scroll_y_offset_px;
let inner_text = Div::new()
    .flex_col()
    .mt(scroll_shift)   // ← layout mutation, forces needs_layout = true
    .children(text_lines)
```

**Example (target pattern):**
```rust
// In a new TextAreaElement::paint() — paint-only, no layout mutation
fn paint(&mut self, state: &mut Self::RequestLayoutState, cx: &mut PaintContext) {
    let offset = self.scroll_y_offset_px;
    cx.push_clip(state.bounds);
    if offset > 0.0 {
        cx.push_offset(0.0, -offset);
    }
    // paint children (all at computed layout positions)
    for child in &mut self.children {
        child.paint(cx);
    }
    if offset > 0.0 {
        cx.pop_offset();
    }
    cx.pop_clip();
}
```

### Pattern 3: Per-View Paint Command Cache

**What:** Store the `Vec<PaintCommand>` output for views that don't change during editor
scroll. On scroll frames, replay the cached slice instead of re-running the element pipeline.

**Zed GPUI reference:** `reuse_paint(range: Range<PaintIndex>)` copies cursor styles,
mouse listeners, and input handlers from the previous frame's rendered output. For ora,
the equivalent is storing `Vec<PaintCommand>` per view and re-appending it when clean.

**Views that are clean during editor scroll:**
- `TabBarView` — content changes only on tab switch or open/close
- `StatusBarView` — content changes only on cursor move or file save
- `SidebarView` (header/tree structure) — changes only on file tree mutations
- `GutterView` — changes content per scroll (line numbers change), but NOT structure

**Views that ARE dirty on every editor scroll frame:**
- `TextAreaView` — visible_lines content changes
- `GutterView` — line numbers change (though layout is stable)

**Implementation sketch:**
```rust
// In OraApp or per-view wrapper
struct ViewPaintCache {
    commands: Vec<PaintCommand>,
    // Key identifying when cache is valid
    scroll_y: usize,        // for editor views
    tab_gen: u64,           // generation counter for tab bar
    // etc.
}
```

**Simpler alternative — generation counter approach:**
```rust
struct PaintCacheEntry {
    generation: u64,        // last frame generation when this was produced
    commands: Vec<PaintCommand>,
}

// In event_loop:
tab_bar_generation: u64,    // bumped only on tab open/close/switch
status_bar_generation: u64, // bumped only on cursor move / file save
sidebar_generation: u64,    // bumped only on file tree change
```

### Pattern 4: Dirty View Set

**What:** A `dirty_views: HashSet<ViewId>` tracks which views need re-rendering. During a
scroll frame, only editor-content views are marked dirty; static chrome views are clean.

**Zed GPUI reference:** `dirty_views: FxHashSet<EntityId>` in Window struct. Views check
`window.dirty_views.contains(&self.entity_id())` during prepaint to decide whether to
replay cached state or run full render.

**For ora:** Views don't have EntityIds in the current architecture. The View trait is
stateless-between-frames (render() is called fresh each frame). The simpler equivalent is
to pass a "dirty" bool to each view's element at render time, or maintain a bitmask of
which UI regions are dirty.

**Recommended approach for ora:** Use a `FrameDirtyFlags` struct on OraApp:
```rust
struct FrameDirtyFlags {
    editor_content: bool,   // true when scroll_y or file content changed
    tab_bar: bool,          // true when tab list changed
    status_bar: bool,       // true when cursor/file status changed
    sidebar: bool,          // true when file tree changed
    gutter: bool,           // true when scroll_y changed (but not layout)
}
```
Views receive their dirty flag and either run full paint or replay cache.

### Pattern 5: UniformList-style Virtual Scrolling (Sidebar)

**What:** Zed's `UniformList` computes which items are visible mathematically using
`first = floor(-scroll_offset.y / item_height)` and `last = ceil((-scroll_offset.y +
viewport_height) / item_height)`. Items are positioned at
`origin + scroll_offset + point(0, item_height * ix)` without relayout.

**For sidebar:** The current sidebar uses `ScrollArea` which applies `PushOffset`. This
already works correctly. The success criterion says "sidebar scroll with viewport
virtualization still works correctly with the new dirty-checking system" — meaning we must
ensure that when sidebar scroll changes, `sidebar: true` is set in dirty flags, triggering
a full re-render of that view rather than replaying stale cache.

### Anti-Patterns to Avoid

- **Margin-top for fractional scroll:** Any `mt(scroll_y_offset_px)` value in a view's
  element tree creates a layout dependency on scroll state. Remove all such uses.
- **Cloning visible_lines unnecessarily:** `TextAreaView::new(model)` clones the full
  `visible_lines` vec. Consider passing a reference or using a generation ID to skip
  clone when content is unchanged.
- **Invalidating too broadly:** Marking all views dirty on scroll defeats the purpose.
  Only mark views whose content actually changes.
- **Cache key mismatch:** If a view is replayed from cache but the scroll offset changed
  its hitbox positions, mouse events will route incorrectly. Hitboxes must also be updated
  on scroll — or derived from stable layout coordinates.

## Common Pitfalls

### Pitfall 1: Scroll Forces needs_layout = true Today

**What goes wrong:** The scroll handler at event_loop.rs:958 unconditionally sets
`needs_layout = true`. Even if layout outputs are stable, this causes compute_flexbox
to run every scroll frame.
**Why it happens:** The comment says "element count and LayoutId assignment order" changes,
which was true before Phase 13.1's glyph cache but may be partially stale now.
**How to avoid:** After removing `mt(scroll_y_offset_px)` from element trees, verify that
`new_layout_count == cached_layout_outputs.len()` holds across scroll frames. Only then
remove the `needs_layout = true` in the scroll handler.
**Warning signs:** Elements becoming invisible or mispositioned after removing the flag.

### Pitfall 2: Hitbox Positions Become Stale

**What goes wrong:** If paint commands are cached and replayed, but the displayed content
has moved (e.g., sidebar scroll changed the visible items), then hitbox positions are wrong.
**Why it happens:** Hitboxes are registered in prepaint and stored in `self.hitboxes`. If
prepaint is skipped (replayed), the hitboxes from the previous frame are used. If scroll
moved content, click positions won't match.
**How to avoid:** For views with scroll (sidebar), always re-run prepaint to update
hitboxes, even if paint is cached. For views without scroll (tab bar, status bar), cached
hitboxes ARE valid since content positions are stable.

### Pitfall 3: PaintCommand::Text Owns glyphon::Buffer

**What goes wrong:** `PaintCommand::Text` contains a `glyphon::Buffer` (owned, not
reference-counted). Caching these commands means holding Buffers for multiple frames.
**Why it happens:** The text pipeline hands ownership of shaped Buffers to paint commands.
After `render_frame()`, buffers are returned to the glyph LRU cache.
**How to avoid:** Cached paint commands for static views (tab bar, status bar) hold Buffers
between frames. This is fine as long as the cache is invalidated when content changes.
The cache for a view must be dropped (Buffers returned to glyph cache) before new commands
are generated for that view.

### Pitfall 4: The mt() Margin Change is a Layout Dependency

**What goes wrong:** `Div::new().mt(scroll_shift)` where `scroll_shift` changes per frame
creates a layout node whose size depends on scroll state. Even if size is unchanged (mt
doesn't affect intrinsic size, only position), it invalidates flexbox cache reasoning.
**Why it happens:** `mt()` modifies the Style's margin. The flexbox engine sees different
styles between frames and cannot be sure output is identical.
**How to avoid:** Move ALL fractional scroll offset application to PaintContext::push_offset.
In ora, this means converting the TextAreaView/GutterView layers that use `.mt(scroll_shift)`
to use `PushOffset` in their paint phase instead.

### Pitfall 5: Element Count Changes on Line-Boundary Scroll

**What goes wrong:** When `scroll_y` advances by one line, `visible_lines[0]` is now
`old_visible_lines[1]`, but the same NUMBER of lines exists. The element count is stable.
However, the current code path also calls `dispatch_command(Scroll(line_delta))` which
may change `viewport_lines` if the adapter recalculates something. This must not happen.
**How to avoid:** Ensure `viewport_lines` is only recalculated on resize, not on scroll.
Verify the adapter's `scroll_y()` change does not alter `viewport_lines()`.

### Paint command cache per static view:
```rust
/// Cached paint output for a view that rarely changes.
struct ViewPaintCache {
    /// Paint commands from last render. None if not yet cached.
    commands: Option<Vec<PaintCommand>>,
    /// Generation when cache was last filled.
    /// Bump this to force cache invalidation.
    generation: u64,
}

impl ViewPaintCache {
    /// Replay cached commands into paint_cx if available and still valid.
    /// Returns true if cache was replayed (caller should skip re-render).
    fn try_replay(&self, current_gen: u64, paint_cx: &mut PaintContext) -> bool {
        if let Some(ref cmds) = self.commands {
            if self.generation == current_gen {
                paint_cx.paint_commands.extend(cmds.iter().cloned());
                return true;
            }
        }
        false
    }
}
```

## State of the Art

| Old Approach | Current Approach | Target Approach | Impact |
|--------------|------------------|-----------------|--------|
| needs_layout=true always | needs_layout=true on scroll | needs_layout=false on scroll | Eliminates flexbox on scroll frames |
| No command cache | No command cache | Per-view command cache for static views | Eliminates prepaint/paint for tab bar, status bar |
| mt() for fractional offset | mt(scroll_shift) in Div | push_offset() in paint | Removes layout dependency on scroll px |
| Full element rebuild | Full element rebuild per frame | Stable element count; content-only refresh | Keeps LayoutIds stable across scroll |

**Key insight from Zed GPUI:** The separation between view-level dirty tracking and
paint command caching is important. Even without full dirty tracking (which requires views
to have stable identities), paint command caching for known-stable regions (tab bar, status
bar) gives most of the benefit with much less complexity.

## Open Questions

1. **Does `mt()` affect flexbox size computation?**
   - What we know: `margin-top` in flexbox shifts an element downward relative to its
     container. It does NOT change the element's intrinsic size. But it DOES change the
     layout node's bounds (origin.y shifts). So `mt(-scroll_y_offset_px)` changes the
     computed bounds returned by `cx.bounds(layout_id)` each frame.
   - What's unclear: Does the flexbox engine recompute if margin changes but parent size
     is unchanged? The current implementation always recomputes from scratch when
     `run_full_layout = true`. When we avoid full layout, we use cached bounds — but those
     cached bounds include the old margin offset. This means PushOffset is the RIGHT
     approach: remove mt() entirely and shift in paint without touching layout bounds.
   - Recommendation: Remove all `mt(scroll_shift)` from TextAreaView and GutterView.
     Apply the offset purely in paint via `push_offset`.

2. **Is the element count truly stable across scroll frames?**
   - What we know: `visible_lines` has `viewport_lines` entries. `viewport_lines` is
     set on resize. On scroll, `scroll_y` changes but `viewport_lines` is stable.
   - What's unclear: Does any code path recompute `viewport_lines` during scroll handling?
     Need to verify the adapter's behavior when `dispatch_command(Scroll(delta))` is called.
   - Recommendation: Add an assertion in debug builds: `assert_eq!(new_layout_count,
     cached_layout_outputs.len())` on scroll frames (when needs_layout was not set true).

3. **PaintCommand::Text buffer ownership in cache**
   - What we know: `PaintCommand::Text` owns a `glyphon::Buffer`. Caching these commands
     means the buffer stays alive between frames. The glyph LRU cache returns buffers after
     `render_frame()` only for commands that had `cache_key: Some(...)`.
   - What's unclear: If a cached command's buffer is returned to the LRU cache while the
     cache entry still holds the PaintCommand, the next frame will try to replay a command
     with an invalidated buffer pointer.
   - Recommendation: For cached views, do NOT return their buffers to the LRU cache.
     Only return buffers from frames where the view was re-rendered (not replayed).
