**In core_editor/src/app.rs — get_open_views_info():**

Currently iterates `self.workspace.views()` which is HashMap iteration (random order). Change to iterate `self.workspace.tab_order()`:

```rust
fn get_open_views_info(&self) -> Vec<(u64, String, bool, bool)> {
    let active_view_id = self.workspace.active_view_id();

    self.workspace.tab_order()
        .iter()
        .filter_map(|view_id| {
            let view = self.workspace.view(*view_id)?;
            let doc = self.workspace.document(view.document_id())?;
            let title = doc.title();
            let is_active = Some(*view_id) == active_view_id;
            let is_dirty = doc.is_dirty();
            Some((view_id.as_u64(), title, is_active, is_dirty))
        })
        .collect()
}
```

  <name>Task 2: Add click handlers for tab switching and closing</name>
  <files>ora/src/views/tab_bar.rs</files>
  <action>
The tab bar needs to dispatch EditorCommands when tabs or close buttons are clicked. The tab bar does NOT have direct access to the adapter — it renders Div elements that the framework's event system handles.

**Approach:** The ora framework uses on_click callbacks on elements like Button, Tab, ListItem. Check how existing click handlers work (e.g., Button.on_click, dialog buttons). The tab bar currently uses raw Div elements for tabs. Two options:

Option A: Use the ora Tab element (`ora/src/elements/tab.rs`) which already has on_click support. The TabBarView currently builds Divs manually — refactor to use the Tab widget.

Option B: Add on_click support to Div (if not already present) and use it directly.

Given that the Tab element exists with on_click, prefer Option A. However, Tab element may not support all the visual customization needed. Check the Tab element API.

If Tab element is suitable, refactor render_tab to use it. If not, the simpler path: the tab bar doesn't need framework-level click handling for the initial implementation. Instead, use the existing EditorCommand dispatch pattern.

**The actual mechanism**: Look at how the event_loop handles mouse clicks. The framework does hit-testing against element bounds during prepaint. For the tab bar, since tabs are Div elements without click handlers, clicks currently do nothing.

The cleanest approach: Pass a callback closure or command channel to TabBarView so it can attach click handlers. TabBarView needs access to an adapter reference or a command sender to dispatch SwitchTab/CloseTab.

**Recommended implementation:**

1. Add `on_tab_click` and `on_tab_close` callback fields to TabBarView:
```rust
pub struct TabBarView {
    presentation: TabBarPresentation,
    on_tab_click: Option<Box<dyn Fn(u64)>>,    // view_id
    on_tab_close: Option<Box<dyn Fn(u64)>>,    // view_id
}
```

2. Add builder methods:
```rust
pub fn on_tab_click(mut self, f: impl Fn(u64) + 'static) -> Self { ... }
pub fn on_tab_close(mut self, f: impl Fn(u64) + 'static) -> Self { ... }
```

3. In render_tab, check if the existing elements (Div) can support click callbacks. Check `ora/src/elements/div.rs` for on_click or on_mouse_down.

If Div does NOT have on_click: Use the Tab widget element instead, or add on_mouse_down to Div. Check what primitives support click handling.

If no primitive supports arbitrary click handling on Div: The alternative is to handle it at the event_loop level by checking if a click falls within tab bar bounds and determining which tab was hit by x-position. This is how many immediate-mode UIs work.

**Pragmatic path if framework click support is limited:**
- Store tab bounds during layout/paint in a shared structure
- In the event_loop mouse_down handler, check if click is within tab bar area
- Calculate which tab was clicked based on x-position and tab widths
- Dispatch SwitchTab(view_id) or CloseTab accordingly

Look at how the existing sidebar file click handler works (`open_file_from_sidebar` in app.rs) for the pattern used in this codebase. The sidebar uses arrow-key navigation + Enter, not mouse clicks on items. So mouse click on tabs may need a new mechanism.

**Simplest viable approach:** Since the EditorRootView (or AppLayout) owns the adapter reference, and TabBarView renders within that context: pass the adapter Rc<RefCell<>> to TabBarView, and in render_tab, create Div wrappers that store the adapter ref and dispatch on click events.

Investigate the codebase's click handling before implementing. Use whichever pattern already exists. If no pattern exists for clickable arbitrary elements, create a minimal one. The key deliverable: clicking a tab dispatches SwitchTab, clicking X dispatches CloseTab.

Also add middle-click (mouse button 2) on a tab to close it, per CONTEXT.
