# Phase 8.1: GPU Layered Rendering Pipeline - Research

**Researched:** 2026-03-02
**Domain:** wgpu multi-pass rendering, glyphon TextRenderer lifecycle, Rust borrow checker constraints
**Confidence:** HIGH

## Summary

The core bug is confirmed: `render_frame()` collects ALL rects into one batch, then ALL text into one
batch, and renders them in two sequential draw calls within a single render pass. This means editor
text (collected early, rendered last) visually appears on top of the command palette background
(collected later as a rect, rendered before text). The `LayerBoundary` markers in the paint command
stream are present but ignored.

The fix requires splitting rendering into per-layer groups: for each layer boundary, flush the
accumulated rects and text before starting the next layer. The primary technical question was whether
glyphon's `TextRenderer.prepare()` can be called multiple times per frame. **It cannot** — each call
to `prepare()` begins with `self.glyph_vertices.clear()`, erasing the previous call's glyph data.
The correct approach is to maintain **multiple `TextRenderer` instances** (one per layer), all sharing
one `TextAtlas` and `Cache`. wgpu supports multiple render passes per frame via a single command
encoder using scoped blocks with `LoadOp::Load` on subsequent passes — this was a real bug in early
wgpu but was fixed via PR #595 and is reliable in wgpu 23.

**Primary recommendation:** Use multiple `TextRenderer` instances sharing one `TextAtlas`, with one
render pass per layer group. First pass uses `LoadOp::Clear`; subsequent passes use `LoadOp::Load`.
The `RectangleRenderer` must be restructured to remove the `&'a self` lifetime from `render()` to
allow it to be called multiple times across pass boundaries.

### Pattern 1: Layer Grouping from Paint Commands

**What:** Group the paint command stream by `LayerBoundary` markers, producing ordered groups of
`(Vec<RectInstance>, Vec<TextEntry>)`.

**When to use:** Before any rendering begins, in a single pass over `commands`.

**Example:**
```rust
// Source: derived from existing gpu.rs pattern + context analysis
struct LayerGroup {
    rect_instances: Vec<RectInstance>,
    text_entries: Vec<TextEntry>,
}

fn group_commands(commands: &[PaintCommand], window_size: (u32, u32)) -> Vec<LayerGroup> {
    let mut groups = vec![LayerGroup::default()];
    for command in commands {
        let current = groups.last_mut().unwrap();
        match command {
            PaintCommand::LayerBoundary => {
                groups.push(LayerGroup::default());
            }
            PaintCommand::StyledRect { bounds, style } => {
                current.rect_instances.push(RectInstance::from_style(style, bounds, window_size));
            }
            PaintCommand::Text { buffer, left, top, bounds, color } => {
                current.text_entries.push(TextEntry { ... });
            }
            // Rect, SetScissor, ResetScissor handled similarly
            _ => {}
        }
    }
    groups
}
```

### Pattern 2: Multiple TextRenderer Instances, Shared TextAtlas

**What:** glyphon's `TextAtlas` and `Cache` are shared across multiple `TextRenderer` instances.
Each `TextRenderer` holds its own `vertex_buffer` and `glyph_vertices` — calling `prepare()` on
each independently populates them without conflict.

**Why this works:**
- `TextRenderer.prepare()` starts with `self.glyph_vertices.clear()` — it replaces, not appends
- Multiple renderers each have their own `glyph_vertices` vec and `vertex_buffer`
- The `TextAtlas` is the shared GPU texture atlas — glyphs rasterized for one renderer are cached
  and reused by others
- `TextRenderer::new()` takes `&mut atlas` but only uses it to call `atlas.get_or_create_pipeline()`
  which deduplicates pipelines via `Cache` — all renderers share the same pipeline

**Example:**
```rust
// Source: glyphon-0.7.0/src/text_render.rs + text_atlas.rs analysis
pub struct TextSystem {
    font_system: FontSystem,
    swash_cache: SwashCache,
    cache: Cache,
    atlas: TextAtlas,
    viewport: Viewport,
    // One TextRenderer per layer, created on demand
    layer_renderers: Vec<TextRenderer>,
    // Pending entries per layer (indexed to match layer_renderers)
    pending_layers: Vec<Vec<TextEntry>>,
}

impl TextSystem {
    pub fn ensure_layer_renderers(&mut self, device: &Device, count: usize) {
        while self.layer_renderers.len() < count {
            let renderer = TextRenderer::new(
                &mut self.atlas,
                device,
                MultisampleState::default(),
                None,
            );
            self.layer_renderers.push(renderer);
            self.pending_layers.push(Vec::new());
        }
    }

    pub fn prepare_layer(
        &mut self,
        device: &Device,
        queue: &Queue,
        layer_idx: usize,
        window_width: u32,
        window_height: u32,
    ) -> Result<(), glyphon::PrepareError> {
        self.viewport.update(queue, Resolution { width: window_width, height: window_height });
        let entries = &self.pending_layers[layer_idx];
        let text_areas: Vec<TextArea> = entries.iter().map(|e| TextArea { ... }).collect();
        self.layer_renderers[layer_idx].prepare(
            device, queue, &mut self.font_system,
            &mut self.atlas, &self.viewport, text_areas, &mut self.swash_cache,
        )
    }

    pub fn render_layer<'pass>(
        &'pass self,
        layer_idx: usize,
        render_pass: &mut RenderPass<'_>,  // NOTE: unbounded lifetime on RenderPass
    ) -> Result<(), glyphon::RenderError> {
        self.layer_renderers[layer_idx].render(&self.atlas, &self.viewport, render_pass)
    }
}
```

**Key insight on lifetimes:** glyphon's `TextRenderer::render()` signature is:
```rust
pub fn render(&self, atlas: &TextAtlas, viewport: &Viewport, pass: &mut RenderPass<'_>)
```
The `RenderPass<'_>` has an elided (unconstrained) lifetime — this means `text_renderer.render()`
does NOT borrow `self` into the render pass. You can drop the render pass, create a new one, and call
render again without borrow conflicts. This is the opposite of `RectangleRenderer::render()`.

### Pattern 3: Fix RectangleRenderer render() Lifetime

**What:** The current signature `pub fn render<'a>(&'a self, render_pass: &mut wgpu::RenderPass<'a>)`
ties the render pass lifetime to `self`, preventing multiple calls across pass boundaries.

**Why this is a problem:** With the current signature, once a render pass holds a reference to the
`RectangleRenderer` (via the bind group and pipeline), you cannot drop the pass and start a new one
while the renderer is still borrowed.

**Fix:** Change the signature to break the coupling. The render pass does not need to hold data
from `self` after the function returns — the GPU data is already on the GPU:

```rust
// Source: analysis of wgpu RenderPass API + existing code
pub fn render(&self, render_pass: &mut wgpu::RenderPass<'_>) {
    // Change: &mut RenderPass<'_> instead of &mut RenderPass<'a>
    // This breaks the lifetime tie between self and the render pass
    if self.instance_count == 0 { return; }
    render_pass.set_pipeline(&self.pipeline);
    if let Some(ref bind_group) = self.bind_group {
        render_pass.set_bind_group(0, bind_group, &[]);
    }
    render_pass.draw(0..6, 0..self.instance_count);
}
```

**CAUTION:** The reason `&'a self` was originally needed: `set_bind_group()` and `set_pipeline()`
store references to GPU objects that must remain valid for the render pass duration. In practice, the
`RectangleRenderer` (and its bind groups/pipeline) will outlive any render pass since it lives on
`GpuState` which owns the encoder. The `'_` elision is safe here.

**Alternative:** Keep a `Vec<RectInstance>` per layer and use multiple calls to `prepare()` on the
same `RectangleRenderer` (one per layer). This avoids multiple renderer instances but requires the
prepare+render loop pattern.

### Pattern 4: Multi-Pass Render Loop

**What:** Single command encoder, multiple render passes using scoped blocks. First pass clears;
subsequent passes load.

**When to use:** When layer groups have been pre-computed.

**Example:**
```rust
// Source: wgpu multi-pass pattern + glyphon hello-world.rs analysis
pub fn render_frame(&mut self, commands: &[PaintCommand]) -> Result<(), wgpu::SurfaceError> {
    let output = self.surface.get_current_texture()?;
    let view = output.texture.create_view(&TextureViewDescriptor::default());

    // Step 1: Group commands by layer
    let layer_groups = group_commands(commands, self.size);
    let layer_count = layer_groups.len();

    // Step 2: Ensure enough TextRenderer instances
    self.text_system.ensure_layer_renderers(&self.device, layer_count);

    // Step 3: Prepare all layers (CPU-side, before any render passes)
    for (i, group) in layer_groups.iter().enumerate() {
        self.text_system.add_layer_entries(i, &group.text_entries);
        self.rect_renderer.prepare(&self.device, &self.queue, &group.rect_instances);
        self.text_system.prepare_layer(&self.device, &self.queue, i, self.size.0, self.size.1)?;
        // PROBLEM: rect_renderer.prepare() overwrites — need separate rect state per layer
        // Solution: see RectLayer approach below
    }

    let mut encoder = self.device.create_command_encoder(&CommandEncoderDescriptor { ... });

    // Step 4: Render each layer in order
    for (i, group) in layer_groups.iter().enumerate() {
        {
            let load_op = if i == 0 {
                LoadOp::Clear(wgpu::Color { r: 0.1, g: 0.1, b: 0.12, a: 1.0 })
            } else {
                LoadOp::Load  // Preserve previous layers
            };

            let mut render_pass = encoder.begin_render_pass(&RenderPassDescriptor {
                color_attachments: &[Some(RenderPassColorAttachment {
                    view: &view,
                    ops: Operations { load: load_op, store: StoreOp::Store },
                    ..
                })],
                ..
            });

            // Draw rects for this layer
            self.rect_renderer.render(&mut render_pass);  // after lifetime fix

            // Draw text for this layer
            self.text_system.render_layer(i, &mut render_pass)?;
        } // render_pass dropped here — borrow released
    }

    self.queue.submit(std::iter::once(encoder.finish()));
    output.present();
    self.text_system.clear();

    Ok(())
}
```

### Pattern 5: Per-Layer Rect Storage

**What:** The `RectangleRenderer` uses a single `instance_buffer` and `bind_group`. Calling
`prepare()` multiple times overwrites previous data (similar to glyphon). Per-layer rects need a
different strategy.

**Options (in order of preference):**

**Option A — Sorted single batch with instanced offset:** Group all layer rects into one buffer but
track per-layer start offsets and draw counts. Use `render_pass.draw(0..6, start..end)` for each
layer's slice.

```rust
// Source: wgpu RenderPass.draw() API — instance_range parameter
render_pass.draw(0..6, layer_start..layer_end);  // Draw only this layer's instances
```

This is the most efficient approach — one prepare, multiple draw calls with different ranges.

**Option B — Multiple RectangleRenderer instances:** One per layer, each with its own buffer.
Simple but wastes GPU memory.

**Option C — Dynamic offsets via storage buffer:** Upload all instances to one buffer, use a
uniform/push_constant for the layer offset. Requires shader modification.

**Recommended: Option A** — pack all instances sorted by layer into one buffer, record per-layer
offsets, use draw range slicing.

```rust
struct LayerRects {
    instances: Vec<RectInstance>,   // All layers concatenated
    layer_ranges: Vec<Range<u32>>,  // [0..5, 5..12, 12..12] for 3 layers
}
```

### Anti-Patterns to Avoid

- **Calling `TextRenderer.prepare()` twice on same instance:** Second call clears first call's
  glyph data. All text for a given layer must be prepared in a single `prepare()` call.
- **Submitting multiple command buffers per frame:** wgpu issue #5663 documents that submitting
  separate command buffers per frame causes hangs on Vulkan. Use ONE encoder for the whole frame.
- **`LoadOp::Clear` on all passes:** Each clear resets the framebuffer, erasing previous layers.
  Only the first pass should clear; subsequent passes must use `LoadOp::Load`.
- **`LoadOp::Load` without a prior render:** If a texture was never written this frame, `LoadOp::Load`
  is technically undefined behavior on Vulkan (loads garbage). Always `LoadOp::Clear` the first pass.
- **Dropping and recreating TextRenderer per frame:** TextRenderer construction calls
  `atlas.get_or_create_pipeline()` which does GPU work. Reuse instances frame-to-frame.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Text layer isolation | Custom glyph batching | Multiple TextRenderer instances | Correct by construction; glyph_vertices Vec is per-instance |
| Multi-pass composition | Custom framebuffer management | wgpu LoadOp::Load | Built into wgpu, handles image layout transitions correctly |
| Instance range draws | Custom draw-indirect | render_pass.draw(0..6, start..end) | Built into wgpu draw call API |

**Key insight:** The glyphon `Cache` type is designed for multi-renderer sharing. `TextRenderer::new()`
takes `&mut TextAtlas` to register a pipeline, not to take exclusive ownership. Multiple renderers
sharing one atlas is the intended pattern per the cache design.

## Common Pitfalls

### Pitfall 1: prepare() Overwrites Previous Data

**What goes wrong:** Calling `text_renderer.prepare()` a second time on the same instance clears
`glyph_vertices` (line 137 of text_render.rs: `self.glyph_vertices.clear()`). The second prepare
only contains the second batch of text areas — the first batch is lost.

**Why it happens:** glyphon's design assumes one `prepare()` call per frame per `TextRenderer`. It
replaces, it does not accumulate.

**How to avoid:** Assign one `TextRenderer` per layer. Never call `prepare()` twice on the same
instance in one frame.

**Warning signs:** Text from lower layers disappears entirely when an overlay is open.

### Pitfall 2: Submitting Multiple Command Buffers Per Frame

**What goes wrong:** Calling `queue.submit()` multiple times per frame (once per render pass) causes
hangs on Vulkan backends (wgpu issue #5663).

**Why it happens:** Swapchain texture is acquired once; the Vulkan presentation engine expects a
single command buffer submission for that texture.

**How to avoid:** Use one `CommandEncoder` for the entire frame. Create multiple render passes
within it using scoped blocks. Submit once at the end.

**Warning signs:** App hangs or `surface.get_current_texture()` returns timeout errors.

### Pitfall 3: RectangleRenderer::render() Lifetime Tie

**What goes wrong:** Current signature `fn render<'a>(&'a self, render_pass: &mut RenderPass<'a>)`
ties the render pass lifetime to the renderer. Cannot drop the render pass and call `render()` again
from the same renderer with the current Rust borrow rules.

**Why it happens:** The `'a` lifetime forces the render pass to stay alive as long as the renderer
borrow, making it impossible to close one render pass and open another while using the same renderer.

**How to avoid:** Change to `fn render(&self, render_pass: &mut RenderPass<'_>)`. The GPU objects
referenced in `set_bind_group()` and `set_pipeline()` live on the `GpuState` struct which outlives
all render passes — the lifetime constraint is unnecessarily strict.

**Warning signs:** Borrow checker error: "cannot borrow `self.rect_renderer` as mutable because it
is also borrowed as immutable" when trying to start a second render pass.

### Pitfall 4: Missing atlas.trim() on Multi-Renderer Setup

**What goes wrong:** `TextAtlas::trim()` clears `glyphs_in_use` sets, freeing atlas space for glyphs
not referenced this frame. With multiple renderers sharing one atlas, `trim()` must still be called
once per frame (after all rendering), not once per renderer.

**Why it happens:** Each `TextRenderer.prepare()` adds glyphs to `atlas.glyphs_in_use`. `trim()`
only needs to run once to compact; running it multiple times mid-frame would evict glyphs needed by
later layers.

**How to avoid:** Call `atlas.trim()` once at the end of the frame, after all layers have rendered.

**Warning signs:** Glyph corruption or `PrepareError::AtlasFull` after many frames.

### Pitfall 5: Prior Failure Analysis — bind_group Invalidation

**What went wrong:** Prior multi-pass attempts caused "sidebar content loss and empty command palette."

**Likely root cause from source analysis:** The `RectangleRenderer::prepare()` conditionally
recreates `bind_group` when the instance buffer grows (line 258-261 of rectangles.rs):
```rust
self.instance_buffer = device.create_buffer(...);  // New buffer
self.bind_group = None;  // Invalidated!
```
If layer 0 had many rects causing buffer growth, then layer 1's prepare triggered bind_group
invalidation. When layer 0's render pass tried to draw using the now-None bind_group, it silently
skipped (the render check is `if let Some(ref bind_group) = self.bind_group`). This explains silent
content loss without panics.

**How to avoid:** The layered approach MUST pre-size the buffer correctly before any render passes
begin. Option A (sorted single batch) avoids this entirely since `prepare()` is called once.

### Pitfall 6: LoadOp::Load on Uninitialized Texture

**What goes wrong:** Using `LoadOp::Load` on the very first render pass of a frame where the
swapchain texture has not yet been written produces undefined behavior (Vulkan validation: "loadOp ==
LOAD and initialLayout == UNDEFINED").

**How to avoid:** Always use `LoadOp::Clear` for the first render pass of each frame. Only subsequent
passes use `LoadOp::Load`.

**Warning signs:** Vulkan validation layer warnings about LOAD_OP_LOAD with undefined layout. Garbage
pixels on first frame or after resize.

## Open Questions

1. **Dynamic layer count**
   - What we know: The number of `LayerBoundary` markers varies per frame depending on which overlay
     elements are visible (e.g., 1 boundary normally, 2 when command palette is open)
   - What's unclear: What is the maximum realistic layer count? (Likely 2-4)
   - Recommendation: Pool `TextRenderer` instances; grow pool on demand, never shrink. Cap at 8.

2. **Scissor/clip interaction with multi-pass**
   - What we know: `SetScissor`/`ResetScissor` commands appear in the paint stream and are currently
     ignored in `render_frame()` (line 149-151 of gpu.rs)
   - What's unclear: Should scissor state carry across layer boundaries or reset per layer?
   - Recommendation: Scissor is a render pass state — reset to viewport size at start of each
     layer's render pass, then apply scissor commands within that pass.

3. **Shadow rendering correctness under new layering**
   - What we know: Shadows in `rect.wgsl` render by expanding the quad and using Gaussian falloff.
     The shadow is drawn as part of the same rect draw call (in the fragment shader).
   - What's unclear: If a shadow from an overlay element overlaps content from a lower layer, the
     lower layer's content is already composited. The shadow needs to blend over it via `LoadOp::Load`.
   - Recommendation: This should work correctly with the multi-pass approach since `LoadOp::Load`
     preserves the lower layers for alpha blending. No shader changes needed.

4. **TextRenderer pool growth during atlas resize**
   - What we know: `TextAtlas::grow()` recreates the GPU texture and calls `rebind()` to update
     `atlas.bind_group`. Existing `TextRenderer` instances reference the pipeline from `Cache` (shared)
     but call `atlas.bind_group` during render. If atlas grows between `prepare()` calls for different
     layers, the bind group will be up-to-date by the time render is called (all prepares happen
     before any renders in the proposed flow).
   - What's unclear: Whether atlas growth during a prepare invalidates any already-prepared renderer's
     vertex buffer data.
   - Recommendation: Perform ALL layer prepares before starting ANY render passes. This ensures atlas
     stabilizes before render phase.
